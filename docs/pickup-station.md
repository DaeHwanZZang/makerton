# 픽업스테이션 zone·node·택배 적재 추적 설계

> 상태: **구현 진행 중** (2026-10-31). 10절 1~4단계와 5단계 일부(스테이션 참조·트레이 반납·운영자 정정)를 구현했다.
> 사용법은 [FMS 안내](../fms_server/README.md#픽업스테이션)·[물품 장부](../fms_server/README.md#물품-장부-cargo)·
> [LastGate 안내](../lastgate/README.md)에 있다. 남은 항목은 10절에 표시했다.
> 아래에서 사용자 확정과 구현 제안을 구분한다. 기존 LastGate 배송 연동은 이미 구현되어 있지만,
> 픽업스테이션 전용 zone·node 연결과 FMS 물품별 적재 장부는 아직 없다.
> 이전 초안의 로봇당 1개 제한·node의 zone 내부 제한은 이번 확인으로 대체한다.
> 배송 묶음은 **직사각형 로봇의 두 트레이에 물품 하나씩, 총 2개**로 확정했다.
> 2개가 모여야 출발하며, 현재 LastGate의 2층×8칸 규격은 향후 구현에서 교체한다.

## 1. 사용자 확정 사항

| 항목 | 요구사항 |
|---|---|
| 구성 | 픽업스테이션 하나에 zone 하나와 픽업 node 하나가 함께 존재한다 |
| zone의 역할 | 적재 장치·컨베이어가 있는 영역을 사용자에게 보여준다 |
| node의 역할 | 로봇이 지정 자세로 도착해 택배를 픽업하는 실제 작업 지점이다 |
| node 위치 | zone 내부 또는 인접한 외부에 배치할 수 있다 |
| 로봇 적재부 | 직사각형 로봇을 절반으로 나눈 두 영역에 트레이 하나씩, 총 2개 |
| 트레이 용량 | 트레이 하나에 물품 하나. 로봇 한 대에 최대 2개 |
| 배송 묶음 | 두 트레이에 배정된 물품 2개가 하나의 배송 묶음 |
| 출발 조건 | 물품 2개가 모이고 두 물품의 적재 완료가 확인되어야 출발 |
| 하차 시연 | 작업 위치에 도착한 뒤 DROP으로 해당 물품을 바닥에 내려놓는 것으로 표현 |
| 실제 장치 | 실제 로봇은 매니퓰레이터로 바닥에 내려놓을 예정. 이번 시뮬레이션은 DROP으로 대체 |
| 추적 단위 | FMS가 물품마다 고유 ID를 부여하고 어느 로봇에 실렸는지 관리한다 |

이후 ID 형식·저장 파일·API·상태 이름은 구현을 위한 **제안**이다.

## 2. zone과 node의 의미

```text
  ┌──── 표시용 pickup zone ────┐
  │  적재 장치 · 컨베이어      │
  └─────────────┬─────────────┘
                ● → 픽업 node (x, y, theta)
                    로봇이 정지·방향 정렬 후 PICK 실행
```

- zone 진입·통과·이탈로 픽업을 시작하지 않는다. `pickup` 작업이 있어야 node에서 PICK을 실행한다.
- zone은 주행금지·감속·자동 도킹·장치 제어·물리 충돌 영역으로 사용하지 않는다.
- 장치가 실제로 통로를 막는다면 원본 점유 맵 또는 별도 주행금지구역으로 표현한다.
  표시용 zone을 그리는 것만으로 장치의 충돌 형상이 생성되지는 않는다.
- node는 점 좌표와 방향 `theta`를 가진다. 화면에서는 방향 화살표로 표시한다.
- zone과 node는 같은 맵에 속하며 반드시 1:1로 연결한다. 독립 생성·삭제로 고아 node를 만들지 않는다.
- zone 밖 node도 허용한다. 초기 버전에서는 임의의 인접 거리 상한으로 거절하지 않고,
  편집 화면에서 연결선을 표시해 장치와 인접한 위치인지 사용자가 확인하게 한다.
  자동 거리 제한이 필요해지면 장치 치수와 로봇 접근 거리를 기준으로 별도 정의한다.

## 3. 현재 구현과 추가할 부분

| 현재 코드에서 확인한 상태 | 이번 설계에서 추가할 부분 |
|---|---|
| `common/map_annotations.py`에 pickup zone/type 없음 | 표시용 `ZoneType.PICKUP`, `LocationType.PICKUP` 추가 |
| `NamedLocation`은 이름·맵·자세·종류를 저장 | 픽업 node가 어느 zone에 연결되는지 저장 |
| `task.py`, `route.py`는 pickup/drop을 기존 PICK/DROP 액션으로 변환 | 스테이션 검증과 물품별 적재 장부 연결 |
| Python·C++의 `Action.payload_id`는 문자열 하나 | 물품별 PICK/DROP에 해당 parcel_id를 넣고 트레이와 연결 |
| `locker.py`는 현재 PICK에 보관소 Job ID, DROP에 Job+세대 값을 사용 | 배송 묶음·실행 작업·물품 ID를 구별하고 물품별 액션으로 전환 |
| LastGate는 2층×8칸, S/M/L별 칸 수를 사용하고 물품 1개도 발행 | 두 트레이에 물품 하나씩 배정하고 2개가 모여야 발행 |
| 현재 FMS 연동은 같은 세대의 여러 물품을 한 DROP으로 처리 | 같은 목적지여도 물품별 DROP과 배송 결과를 각각 관리 |
| LastGate에 접수번호 `receipt_no`가 이미 있음 | 원본 접수번호를 보존하며 FMS 고유 물품 ID와 대응 |
| 로봇 `State`에는 실제 적재물 목록이 없음 | FMS가 액션 보고를 바탕으로 적재 장부를 관리 |

PICK/DROP은 현재 C++ 시뮬레이터에서 시간 기반 액션이다. 실제 적재 센서·문 열림·수령 인증은 없다.
따라서 FMS 화면은 **작업 완료 보고로 확인한 적재 상태**를 보여주며 실제 화물을 독립 검출했다고 설명하지 않는다.

## 4. 스테이션 식별·저장 제안

### 4.1 식별자와 연결

- 불변 스테이션 식별자로 `PS-<UUID>`를 사용한다. 별도 ID를 중복 생성하지 않고 pickup zone의 `zone_id`로도 사용한다.
- node는 기존 site `locations.json`의 named location으로 저장하고 `type: pickup`, `zone_id`를 추가한다.
- 스테이션 참조는 `{site_id, map_id, zone_id}`다. 이름은 표시·기존 작업 편집용이며 식별자가 아니다.
- 같은 zone에 pickup location 두 개를 연결하거나 node 없이 zone만 등록하는 요청은 거절한다.
- 작업의 `OrderNode.node_id`는 실행할 때 생성되는 노드 ID다. 맵에 저장하는 픽업 지점의 식별자와 구별한다.

```text
맵 버전 annotations.json
  zones[]: {zone_id: "PS-…", type: "pickup", name, polygon}

site locations.json
  "보관소 A": {map_id, x, y, theta, type: "pickup", zone_id: "PS-…", ...}
```

스테이션 표시 이름은 연결된 location 이름을 기준으로 한다. 이름 변경 때문에 zone의 ID나 위치를 바꾸지 않는다.

### 4.2 생성·편집·검증

1. 맵의 **＋ → 픽업스테이션**에서 사각형 zone을 그린다.
2. 같은 맵에서 node 위치를 클릭하고 방향을 지정한다. zone 밖도 선택할 수 있다.
3. 이름·영역·node 방향을 미리 본 뒤 한 번에 저장한다.

검증은 다음과 같다.

- zone의 유효 사각형·맵 범위, node의 유한 좌표·유효 각도·동일 맵·FREE 셀을 검사한다.
- UNKNOWN·맵 밖·주행금지 위치의 node는 거절한다. **zone 내부 포함 여부는 거절 조건이 아니다.**
- FREE 셀은 로봇이 도달 가능하다는 충분조건이 아니다. 주변 여유·경로는 별도로 검사하고,
  아직 생성되지 않은 경로나 다른 로봇까지 고려한 도달 가능성을 보장한다고 설명하지 않는다.
- 이름 중복과 1:1 연결 위반을 거절한다.
- zone 변경은 기존 맵 버전 체계에 따라 새 버전을 만든다. pickup을 장애물로 굽지는 않는다.
- node 자세 변경은 location 수정으로 처리한다. 이미 발행한 작업의 좌표 스냅샷은 유지한다.
- 스테이션을 사용하는 진행·대기 작업, 배송 설정, 미반납 물품이 있으면 삭제를 거절한다.
  임대 중인 node의 위치 변경도 거절한다. 단순 이름 변경은 불변 참조를 유지한다.
- 일반 zone/location API로 pickup을 부분 생성·삭제하거나 다른 타입으로 바꾸는 우회를 막는다.

### 4.3 저장 일관성

맵 버전과 locations.json은 별도 파일이므로 락만으로 프로세스 중단 시 원자성이 보장되지는 않는다.
기존 `_EDIT_LOCK → locations._lock` 순서를 유지하고, 스테이션 생성·수정·삭제의 작업 기록을 먼저 저장한다.
재시작 시 두 저장소의 연결을 대조하고 완료 또는 원복한다. 복구되지 않은 스테이션은 작업 대상으로 노출하지 않는다.

`ZoneType._missing_`은 현재 알 수 없는 종류를 PROHIBIT로 처리한다.
common·viewer 사본, 맵 인제스트·굽기 경로를 함께 갱신해 pickup이 진입금지로 변하지 않게 해야 한다.

## 5. 배송 묶음·트레이·물품 ID

### 5.1 두 트레이와 출발 조건

```text
         직사각형 로봇의 적재부
  ┌─────────────────┬─────────────────┐
  │    TRAY_A       │    TRAY_B       │
  │    물품 P1      │    물품 P2      │
  └─────────────────┴─────────────────┘
       물품 2개 = 배송 묶음 B1
```

- TRAY_A/B는 로봇 안에서 유지하는 고정 슬롯 이름이다. 배송이 바뀌어도 트레이 ID는 바뀌지 않는다.
- 실제 배치를 앞/뒤로 나눌지 좌/우로 나눌지는 아직 지정하지 않았다. 위 그림은 두 구획의 개념도다.
- 빈 트레이와 물품이 있는 트레이를 구분한다. 한 트레이에 두 물품을 넣거나 한 물품이 두 트레이를 차지하지 않는다.
- 물품 크기 S/M/L가 트레이 적합성 검사에 쓰일 수는 있지만, 작은 물품 여러 개를 한 트레이에 담지는 않는다.
  트레이의 실제 치수·허용 중량·수용 가능한 크기 기준은 아직 미정이다.
- 대기 물품이 하나뿐이면 보관소에 대기시킨다. 2개가 모여야 새 배송 묶음을 만들고 로봇을 보낸다.
- 예상 묶음을 보낸 뒤 직접 수령·수령 방식 변경으로 후보가 줄면, 최종 적재 확정 직전에 다시 2개인지 확인한다.
  대체할 물품이 없어 1개가 되면 PICK을 시작하지 않고 묶음을 취소한다. 로봇은 node를 비운 뒤 예약을 해제한다.
  남은 물품은 보관소 대기 상태로 돌려 다음 짝을 기다린다.
- 두 물품이 적재된 뒤 하나를 배송하면 다른 하나가 남은 상태로 다음 목적지로 이동한다.
  **출발 시 2개 조건은 보관소에서 새 배송을 시작하는 조건**이며, 첫 배송 뒤 로봇이 멈춰 있어야 한다는 뜻은 아니다.
- 배송 중 빈 트레이에 새 물품을 추가하지 않는다. 해당 묶음의 배송·반납 처리를 닫은 후 다음 묶음을 시작한다.

### 5.2 ID의 책임

| ID | 소유 | 의미 |
|---|---|---|
| `receipt_no` | LastGate | 택배 접수 원본 번호. 유지한다 |
| `parcel_id` | FMS | 물품 하나의 고유 ID. 예: `P-<UUID>` |
| `bundle_id` | FMS | 물품 2개로 구성한 한 번의 배송 묶음. 예: `B-<UUID>` |
| `tray_id` | 로봇 내 고정 | TRAY_A 또는 TRAY_B. 단독으로 전역 물품 식별자가 되지는 않는다 |
| `job_id` / `action_id` | 각 실행 시스템 | 배송·이동 작업과 PICK/DROP 실행을 구별 |

- 송장번호·배송 묶음·물품은 서로 다른 식별 대상이다. 물품마다 ID와 배송 현황을 독립 관리한다.
- LastGate의 `(보관소 식별자, receipt_no)`와 `parcel_id`를 1:1로 연결한다.
- 보관소 식별자는 재시작해도 유지하는 설정값이다. 매 연결마다 달라지는 MQTT client_id를 사용하지 않는다.
- 같은 물품의 중복 메시지·FMS 재시작·배송 실패·재배정에는 기존 parcel_id를 재사용한다.
- 재시도로 다른 물품과 새로 묶으면 새 bundle_id를 발급한다. 기존 물품 ID와 과거 배송 이력은 유지한다.
- 트레이 배정은 최종 묶음 확정 시 저장한다. `(robot_id, tray_id)`에는 진행 중인 물품 하나만 연결할 수 있다.
- DELIVERY_JOB은 예상 목록이다. FMS는 실제 적재 여부를 확정하지 않는다.
  최종 BUNDLE_CONFIRMED가 유효한 물품 2개인지 검사하고, ID·묶음·트레이 배정을 영속 저장한 뒤 PICK을 발행한다.
- 물품은 아직 보관소에 있어도 추적 ID를 가질 수 있다. ID 발급과 물리 적재 완료는 별개의 사건이다.

### 5.3 물품별 PICK/DROP 실행 제안

물품별 상태를 명확히 표현하기 위해 **PICK과 DROP을 물품별 액션으로 분리**하는 방식을 제안한다.
기존 그룹 명세 ID 제안은 이 두 트레이 규격에 맞춰 대체한다.

```text
B1: TRAY_A → P1 → 101동 101호
    TRAY_B → P2 → 101동 102호

보관소 node: PICK(P1) 완료 → PICK(P2) 완료 → 두 트레이 적재 확인 → 출발
101동 101호: 도착 → DROP(P1) 완료 → TRAY_A 비움, P1 배송 완료
101동 102호: 도착 → DROP(P2) 완료 → TRAY_B 비움, P2 배송 완료
보관소 복귀: 묶음 실행 종료 → 다음 묶음 수락
```

- `Action.payload_id = parcel_id`로 보낸다. FMS는 action_id에 bundle_id·robot_id·tray_id를 연결한다.
- 같은 목적지에 두 물품이 가면 이동은 공유할 수 있으나 DROP은 두 번 수행한다.
  첫 DROP만 완료되면 첫 물품만 배송 완료이며 다른 물품은 트레이에 남는다.
- 두 PICK 중 하나만 성공하면 부분 적재 상태로 출발하지 않는다. 실린 물품과 남은 물품을 대조해
  반납 또는 적재 재개를 운영자가 결정한다. 완료 여부가 불확실한 PICK을 자동 반복하지 않는다.
- 물품 순서·목적지·트레이 배정은 발행한 액션 뒤에 임의 변경하지 않는다.
- FMS가 트레이를 추적하므로 현재 문자열 하나인 payload_id로 물품 식별은 가능하다.
  실제 로봇에 트레이 선택 명령을 전달하는 계약은 장치 연동 시 별도로 확정한다.

### 5.4 바닥에 내려놓는 시연

- 실제 로봇의 매니퓰레이터 동작을 시뮬레이션에서는 **작업 지점 도착 → DROP RUNNING → DROP FINISHED**로 대체한다.
- 단순 도착만으로는 배송 완료로 처리하지 않는다. DROP FINISHED를 받아야 한다.
- DROP RUNNING 동안 해당 트레이와 물품을 하차 중으로 표시한다.
- FINISHED 때 해당 트레이를 비우고 물품 상태를 delivered로 바꾼다.
  물품의 마지막 확인 위치는 로봇에서 **도착한 맵·작업 위치의 바닥**으로 옮겨 기록한다.
- 시연 화면에는 해당 위치에 물품 아이콘과 parcel_id를 표시한다. 같은 위치의 물품은 ID 목록으로 구분한다.
- 바닥 표시는 논리적인 하차 결과다. 매니퓰레이터 궤적·그리퍼·화물 낙하·바닥 충돌 물리를 구현하는 것은 아니다.
  별도 팔 모델 추가를 이유로 기존 로봇의 주행 충돌 형상이나 planner 팽창을 바꾸지 않는다.

### 5.5 묶음과 물품의 배송 현황

- 묶음 화면은 두 물품 각각의 목적지·트레이·현재 상태를 보여준다. 묶음 상태만으로 물품 상태를 덮어쓰지 않는다.
- P1 배송 완료, P2 이동 중이면 묶음은 `배송 중 1/2`이며 P1은 delivered, P2는 onboard다.
- 두 물품의 세대 DROP이 모두 확인되면 `배송 완료 2/2`다. 로봇의 보관소 복귀 진행은 별도로 표시한다.
- 하나만 배송되고 다른 하나가 실패·반납되면 `일부 배송`으로 표시한다. 전부 배송 완료로 간주하지 않는다.
- 실행 작업 종료는 물품별 인도·반납 결과와 로봇 복귀가 확인된 뒤 처리한다.

## 6. 적재 상태와 로봇 연결 제안

| 상태 | 의미 | 정상 전이 근거 |
|---|---|---|
| `planned` | 이번 적재 대상. 로봇에 실제로 실렸다고 확정하지 않음 | 최종 적재 목록 저장 |
| `loading` | 적재 진행 | 해당 PICK RUNNING |
| `onboard` | 로봇 적재 확인 | 해당 PICK FINISHED |
| `unloading` | 세대 인도 또는 보관소 반납 진행 | 해당 DROP RUNNING |
| `delivered` | 세대에 인도 완료 | 세대 DROP FINISHED |
| `returned` | 보관소에 반납 완료 | 보관소 반납 DROP FINISHED 또는 운영자 반납 확인 |
| `canceled` | 적재되지 않은 계획 종료 | 미적재 확인과 작업 종료 |
| `unknown` | 액션 결과·실물 위치를 확정할 수 없음 | 적재/하차 중 보고 단절·취소·실패·완료 증거 누락 |

- `assigned_robot_id`와 적재가 확인된 `onboard_robot_id`를 분리한다.
  로봇 배정만으로 적재 목록에 올리지 않는다.
- PICK/DROP FINISHED와 action_id·job·로봇·물품·트레이를 대조한다. 다른 작업이나 오래된 보고로 상태를 바꾸지 않는다.
- RUNNING이 누락되어도 일치하는 FINISHED가 도착하면 완료 증거로 사용할 수 있다.
- 이동 중 통신만 끊겼다면 마지막 확인 상태 `onboard`는 유지하고 통신 끊김을 별도 표시한다.
  통신 단절만으로 물품이 사라졌다고 처리하지 않는다.
- 적재·하차 결과가 불확실하면 `unknown`으로 표시하고 마지막 확인 위치와 후보 로봇을 보존한다.
  로봇의 `order_id`가 비었다는 이유만으로 인도·반납 완료로 바꾸지 않는다.
- 두 물품 중 일부만 실리거나 내려졌다면 각 액션의 완료 증거와 물품별 운영자 확인으로 부분 결과를 기록한다.
- 트레이는 `empty / reserved / loading / occupied / unloading / unknown`을 구분한다.
  unknown 트레이를 빈 것으로 간주하거나 다른 물품에 다시 배정하지 않는다.
- 로봇의 적재 화면은 **확인된 적재물**과 **확인 필요한 물품**을 구분한다.
- 로봇 재시작 뒤 실제 화물이 그대로 있는지는 현재 State로 확인할 수 없다. 해당 로봇의 재적재·다음 배송 전에 대조 절차를 둔다.

## 7. 기존 LastGate 연동과 책임 분리

- LastGate는 접수·계정·수령 방식·보관 위치·고객용 배송 상태의 원본이다.
- FMS는 `parcel_id`·배송 묶음·트레이 연결·물품별 액션·적재 상태·인도/반납 증거의 원본이다.
- 현재 LastGate의 적재 알고리즘은 2층×8칸의 16단위 박스 모델이다. 새 규격은 물품 2개·트레이 2개이므로
  설정의 숫자만 바꾸지 않고 bundler·칸 배정·메시지의 layer/cells·요약·웹 표시·테스트를 함께 전환해야 한다.
  보관소 랙의 S/M/L 분류와 로봇 트레이의 적재 규격은 구별한다.
- 물품 1개도 Job을 만드는 현재 정책을 2개 대기로 바꾸고, 최종 목록에서도 2개를 재검사한다.
- 현재 LastGate의 LOADED는 BUNDLE_CONFIRMED 시점에 설정된다.
  따라서 이를 FMS의 `onboard`와 동일시하지 않는다. FMS는 PICK FINISHED를 따로 기다린다.
- 현재 `locker.py`의 일반 `pickup_target` 연결은 향후 불변 스테이션 참조로 전환한다.
  기존 설정을 이름이 같다는 이유만으로 임의 zone에 연결하지 않는다. 사용자가 스테이션을 선택해 전환한다.
- 기존 접수번호 기반 DELIVERY_RESULT는 유지할 수 있다. FMS가 parcel_id를 receipt_no로 변환해 보고한다.
- DELIVERED는 세대 DROP 확인 후 보고한다. 실패 물품은 보관소 복귀만으로 재입고하지 않고,
  반납이 확인된 뒤 FAILED를 보고한다. JOB_DONE은 남은 물품의 처리가 확인된 뒤 보낸다.
- 물품이 남아 있거나 unknown인 동안 기존 배송 로봇 예약을 유지한다. 다른 배송으로 자동 전환하지 않는다.
- 픽업스테이션 node는 동시에 한 로봇만 사용하도록 임대한다. 이는 **node 작업의 예약**이며
  표시용 zone에 들어온 로봇을 감지·제어하는 기능이 아니다.
- PICK FINISHED만으로 임대를 즉시 풀지 않는다. 로봇이 node를 벗어난 것이 확인된 뒤 해제한다.
  취소·통신 단절 시에도 node가 비었다고 확인되기 전에는 다른 로봇을 보내지 않는다.

## 8. 영속화·재시작 제안

- FMS 데이터 루트의 `cargo.json` 하나에 물품·외부 접수번호 대응·배송 묶음·트레이 배정·액션·처리 이벤트를 저장한다.
  같은 물품의 중복 생성과 중복 액션 적용은 동일 락에서 검사한다.
- 물품 ID·배송 묶음·트레이 배정을 먼저 저장한 뒤 실행 작업에 참조를 연결하고 마지막에 오더를 발행한다.
- `jobs.json`, `locker_deliveries.json`, `cargo.json`의 교차 갱신은 자동으로 원자적이지 않다.
  작업 기록을 먼저 남기고 재시작 시 미완료 연결을 대조한다. 연결이 불확실하면 차단한다.
- 액션 보고를 반영한 장부와 외부로 보낼 결과를 함께 기록한다. 미전송 결과는 중복 안전하게 재전송한다.
- node 임대와 배송 로봇 예약도 시작 시 복원한다. 통신이 끊겼다는 이유로 자동 해제하지 않는다.
- 기동 시 새 parcel_id를 발급하거나 미확인 PICK/DROP을 자동 재발행하지 않는다.
- 기존 단일 FMS 프로세스 운영을 유지한다. 멀티 worker·분산 장부로 확장한 것으로 설명하지 않는다.

## 9. 화면·API 제안

### 화면

- 맵의 픽업스테이션은 반투명 zone·방향 화살표 node·둘 사이 연결선을 함께 표시한다.
- 스테이션 선택 시 이름·ID·맵·node 자세·예약 로봇을 보여준다.
- 로봇 상세에는 직사각형 적재부를 둘로 나누어 TRAY_A/B의 빈 상태·물품 ID·목적지·배송 상태를 보여준다.
- 배송 묶음 상세에는 두 물품과 `0/2 → 1/2 → 2/2` 배송 진행, 로봇 복귀 상태를 구분해 보여준다.
- 맵에는 DROP 완료된 물품의 바닥 위치·ID를 표시하고, 로봇 적재 표시에서 해당 물품을 제거한다.
- 물품 상세에는 현재/마지막 확인 위치, 묶음·트레이·작업, 이력, 운영자 정정 사유를 보여준다.
- unknown 처리에서 물품별로 실물 위치를 선택한다. 일괄 배송 완료를 기본값으로 선택하지 않는다.

### API 방향

| 경로 | 용도 |
|---|---|
| `/api/v1/sites/{site_id}/pickup-stations` | 스테이션 목록 |
| `/api/v1/sites/{site_id}/maps/{map_id}/pickup-stations` | zone+node 동시 생성 |
| `/api/v1/sites/{site_id}/maps/{map_id}/pickup-stations/{station_id}` | 동시 편집·삭제, base_version 검사 |
| `/api/v1/sites/{site_id}/delivery-bundles` | 물품 2개 단위의 배송 묶음과 진행 조회 |
| `/api/v1/sites/{site_id}/parcels` | FMS 물품 장부 조회 |
| `/api/v1/sites/{site_id}/parcels/{parcel_id}` | 물품 상세·이력 |
| `/api/v1/sites/{site_id}/parcels/{parcel_id}/resolve` | 불확실 물품의 실물 위치·사유 기록 |
| `/api/v1/robots/{robot_id}/cargo` | 확인된 적재물·확인 필요한 물품 조회 |

구체적인 요청·응답 필드와 기존 복귀 API의 변경은 구현 착수 시 확정한다.
이번 단계에서는 새 API나 UI가 이미 존재한다고 사용자 안내에 기록하지 않는다.

## 10. 구현 순서와 완료 조건

1. pickup zone/type·viewer 사본·스테이션 zone/node 동시 편집을 추가한다. **(구현됨)**
   - 4.3의 작업 기록(journal) 대신 목록 조회 시 두 저장소를 대조해 broken 표시 → 편집 차단 → 삭제로 정리하는 방식으로 구현했다.
   - node 임대는 아직 없다. 진행 중 작업이 그 이름을 참조하면 node 이동을 거절하는 것으로 대신한다.
2. LastGate 묶음 생성을 2개 대기·두 트레이 배정으로 전환한다. **(구현됨)** `bundler.py`, `fms_adapter.py`(`tray` 필드).
3. FMS 물품 ID·외부 접수번호 대응·배송 묶음·트레이·이력 저장과 재시작 대조를 추가한다. **(구현됨)** `fms_server/cargo.py`.
   - 8절의 결과 발행 기록·미전송 재전송은 기존 `locker_deliveries.json` 재전송을 그대로 쓴다. 별도 이벤트 저장소는 없다.
   - 장부 전이는 보관소 연동 워커가 로봇 State 의 action_states 를 주기 관측해 반영한다(RUNNING 누락 시 FINISHED·작업 성공으로 보정).
4. 기존 PICK/DROP 단일 맵·다층 실행을 물품별 액션과 장부 전이에 연결한다. **(구현됨)**
5. LastGate 설정을 스테이션 참조로 연결하고 반납 확인·운영자 정정·node 임대를 붙인다. **(일부)** 스테이션 참조·트레이 반납 DROP·
   운영자 정정 API는 구현했다. 반납은 픽업 node 의 반납 DROP FINISHED로 확인한다. **node 임대는 아직 없다** —
   LastGate `MAX_ACTIVE_JOBS=1`이라 현재는 한 배송만 스테이션을 쓴다. 로봇 여러 대로 늘리기 전에 필요하다.
6. 두 트레이·물품별 배송·바닥 하차 위치를 표시하고 통합 회귀를 수행한다. **(구현됨)** 로봇 상세 트레이, 맵 바닥 물품, 보관소 화면 묶음·장부.

구현 검증은 다음을 포함한다.

- zone 밖 node 생성 가능, 고아 연결·중복 node·비FREE node 거절.
- pickup zone이 주행금지로 구워지지 않음, common/viewer 계약 일치.
- 물품이 1개면 출발하지 않고 2개면 두 트레이에 하나씩 배정. 세 번째 물품은 다음 묶음으로 대기.
- 최종 적재 목록이 1개로 줄면 픽업하지 않으며, PICK 하나만 성공해도 부분 적재로 출발하지 않음.
- 두 물품 PICK 후 하나만 DROP하면 해당 트레이만 비고 다른 물품은 같은 로봇에 남음.
- 같은 목적지의 두 물품도 물품별 DROP 결과와 배송 현황을 구별.
- DROP 전에는 바닥 물품 표시·배송 완료가 없고 FINISHED 뒤에만 해당 물품이 바닥 위치로 전환.
- 중복 메시지·재시작·실패 후 새 배송에서도 같은 물품 ID 유지.
- FINISHED 전에는 적재·하차 완료로 세지 않음. 완료 증거 누락은 unknown으로 처리.
- 부분 적재·부분 하차 정정, 복귀 후 반납 확인, 배송 결과 중복 재전송.
- node 점유 중 다음 로봇 배정 차단, 통신 단절 후 임대·적재 정보 보존.
